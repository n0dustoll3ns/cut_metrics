# Cut Metrics — бизнес-модель и user journey (контекст для проектирования архитектуры)

## 1. Что это за продукт

Cut Metrics — мобильное приложение (Flutter, Android → в перспективе iOS), которое автоматически собирает данные пользователя из Health-сервиса (вес, сон, шаги, активность), отделяет реальный тренд веса от шумовых ежедневных колебаний и раз в неделю выдаёт короткое саммари с конкретной рекомендацией по корректировке калорийности.

**Проблема, которую решает продукт:** пользователи, которые уже ведут трекинг питания (в MyFitnessPal и аналогах), не получают из существующих инструментов главного — понятного темпа изменения веса в % за неделю и понятного решения "что делать дальше". Вместо этого они вручную сводят данные в таблицах или полагаются на догадки.

**Ключевой принцип продукта (критичен для архитектуры):** минимум действий со стороны пользователя, максимум автоматизации. Любая фича, требующая лишнего ручного ввода данных от пользователя, — под вопросом и требует отдельного обоснования.

## 2. Целевая аудитория

- 18–50 лет, мужчины и женщины, сидячая офисная работа
- Уже используют трекер калорий/еды — это предпосылка использования Cut Metrics, не альтернатива ему
- Осознанно проходят фазу "сушки"/работы над композицией тела, понимают, что это небыстрый процесс
- Могут быть новичками или опытными спортсменами (возможна дальнейшая сегментация фич под эти группы)

## 3. Ядро продукта: логика "мозга" рекомендаций

Это самая ценная и самая сложная для архитектуры часть — рекомендательная логика, основанная на личном методе автора продукта.

### Входные данные (из Health-сервиса)
- Вес (ежедневные замеры, с возможными пропусками дней)
- Сон
- Шаги / активность
- (Данные о питании/калориях пользователь ведёт в стороннем трекере — Cut Metrics их **не** собирает напрямую на старте, только вес/сон/шаги/активность через Health Connect)

### Обработка данных
- Сглаживание сырых ежедневных значений веса через скользящее среднее (EMA) — устраняет шум суточных колебаний (вода, еда, гормональные факторы)
- На основе сглаженного тренда — расчёт **фактического темпа изменения веса в % за неделю**

### Логика рекомендации (ключевой алгоритм)
- Пользователь выбирает целевой темп изменения веса в диапазоне **0.3–1.4% в неделю**:
  - Ниже 0.3% — признано неэффективным (слишком медленно для практической пользы)
  - Выше 1.4% — признано потенциально опасным для здоровья и удержания мышечной массы
  - Внутри диапазона — 2–3 "скорости" на выбор пользователя (например, бережный / стандартный / агрессивный темп)
- Раз в неделю система сравнивает фактический темп с целевым и определяет статус:
  - **В темпе** — фактический темп близок к целевому
  - **Слишком медленно** — рекомендация небольшого снижения калорийности
  - **Слишком быстро** — рекомендация небольшого повышения калорийности / рефида (примечание: логика рефидов на основе автоматических данных пока не проработана — требует данных о калориях, которых нет напрямую в Health-сервисе; на первой версии это не реализуем без ручного ввода, что противоречит принципу минимума действий — оставить как открытый вопрос для будущих версий)
- Результат недели оформляется как короткое саммари: статус + 1–2 предложения рекомендации на следующую неделю

### Важные технические принципы (уже определены ранее в проекте)
- Кэшировать нужно **обработанные** данные, а не сырые — данные из Health-сервиса идемпотентны, повторный запрос даёт тот же результат, поэтому смысла хранить сырьё отдельно нет
- Существующая архитектура (см. `cut_metrics_project_map.md`) разделена на три слоя:
  - `HealthRepository` — доступ к сырым данным
  - `HealthDataProcessor` — агрегация, EMA, дедупликация
  - `ViewModel` — состояние UI и оркестрация, без бизнес-логики
- Эта же логика темпа/рекомендаций должна встраиваться в слой `HealthDataProcessor` (или отдельный сервис-модуль над ним), не в UI/ViewModel

## 4. User Journey

1. **Онбординг:** подключение Health-сервиса → выбор целевого темпа (одна из 2–3 "скоростей" в диапазоне 0.3–1.4%/неделю) → минимум вопросов, никакого дополнительного ручного заполнения профиля сверх необходимого
2. **Ежедневное использование:** пользователь открывает приложение → видит сглаженный тренд веса (главный экран) → никаких действий не требуется, всё уже посчитано автоматически из Health-данных
3. **Еженедельный цикл (ключевая точка ценности):** раз в неделю становится доступным саммари — статус темпа + рекомендация на следующую неделю
4. **Точка монетизации (paywall):** просмотр еженедельного саммари — платная функция (см. бизнес-модель ниже). Свободный доступ к графику тренда и сырым данным остаётся бесплатным всегда
5. **Долгосрочное использование:** пользователь возвращается еженедельно за саммари; ценность накапливается по мере роста истории данных (более точный тренд, более уверенные рекомендации)

## 5. Бизнес-модель и монетизация

### Модель: Freemium
- **Бесплатно, всегда:** сбор данных из Health-сервиса, графики, тренд веса (сглаженное значение)
- **Платно (подписка):** еженедельное саммари с персональной рекомендацией по корректировке — это ядро ценности продукта и единственная платная функция

### Стратегия запуска
- **До набора первой базы пользователей:** полный премиум-доступ бесплатно и безлимитно всем пользователям (порог количества пользователей, после которого включается paywall, — предстоит определить отдельно, зависит от скорости роста и объёма обратной связи, которую нужно собрать)
- **После набора базы:** включается paywall на еженедельное саммари

### Ценообразование
- Базовая единица — **годовая подписка**, ориентир цены — уровень "чашка кофе в год" (крайне низкий ценовой якорь, осознанный выбор для первого продукта)
- **Месячная подписка** = (годовая цена ÷ 12) × 150% — наценка за помесячную гибкость
- Причина выбора низкой цены: простой первый продукт, отсутствие необходимости в сложной ценовой политике на старте, фокус на привлечении и удержании, а не на максимизации ARPU

### Обоснование ценности (для paywall-экрана и коммуникации)
- Экономия времени пользователя: не менее 1 часа в неделю по сравнению с ручным сведением данных
- Освобождение от ментальной нагрузки самостоятельных расчётов и поиска нужных метрик
- Альтернатива без Cut Metrics — разрозненные таблицы/заметки, отсутствие ясного ответа "в темпе ли я"

## 6. Ограничения и приоритеты, важные для архитектуры

- Разработка ведётся одним человеком (автор продукта, он же Flutter-разработчик), в среднем **10 часов в неделю**, без отрыва от основной работы — архитектура должна быть простой в поддержке, без избыточного инжиниринга
- Вся поддержка пользователей на старте — вручную силами автора; автоматизация поддержки — по мере роста нагрузки, не приоритет MVP
- Публичность/маркетинг через контент — пока не в фокусе, весь ресурс уходит в продукт
- Платформа на старте — только Android; архитектура должна закладывать возможность позже добавить iOS без переписывания бизнес-логики (специфична под ОС в первую очередь интеграция с Health-сервисом — HealthKit на iOS против Health Connect на Android)

## 7. Дорожная карта функциональности (укрупнённо)

1. **Уже реализовано (alpha):** сбор данных из Health-сервиса (сон, еда/шаги, активность, вес), построение графиков, отображение тренда веса
2. **В разработке:** расчёт реального расхода калорий за неделю на основе всех собранных данных
3. **Следующий этап:** еженедельное саммари с рекомендацией на основе алгоритма из раздела 3 — это точка, где появляется монетизация
4. **Далее:** виджеты на главный экран устройства
5. **Открытый вопрос (не решён, не должен блокировать MVP):** логика рефидов — требует данных о потреблённых калориях, которых нет в Health-сервисе напрямую; решение пока не найдено без нарушения принципа минимума ручного ввода

## 8. Что нужно агенту при проектировании архитектуры

- Заложить чёткое разделение между бесплатным контуром (сбор данных, тренд) и платным контуром (саммари, рекомендации) — это должно быть легко переключаемым флагом/уровнем доступа, а не жёстко вшитым в код, так как порог перехода на paywall ещё не определён и может меняться
- Рекомендательный алгоритм (раздел 3) вынести в отдельный, тестируемый модуль — это интеллектуальное ядро продукта и будет дорабатываться чаще всего
- Спроектировать так, чтобы добавление новых источников данных (в перспективе — данные о калориях, если появится решение по разделу 7, пункт 5) не требовало переписывания процессора данных
- Учитывать идемпотентность данных Health-сервиса при проектировании кэширования (раздел 3)
