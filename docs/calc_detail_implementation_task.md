# Cut Metrics — задание: реализация «Детализация расчёта» (CalcDetail)

> ТЗ для разработки в СЛЕДУЮЩЕМ чате — ПОСЛЕ дизайн-задания
> `docs/calc_detail_design_task.md` (лист «Как рассчитано» должен существовать в
> `docs/design-system.html` и макетах). Дизайн-референс — секция «Детализация расчёта»
> в `docs/design-system.html` и `docs/screen-today-graph-summary-settings.html`.
> Паттерны Фаз 1–7 — `memory-bank/systemPatterns.md`.
>
> ⚠️ Главное ограничение: формулы и правила расчётов НЕ меняются — фича только
> объясняет существующий расчёт. Любое расхождение итога трассы с числом на экране = баг.

## 0. Решения пользователя (2026-09-23)

1. Формат — единый **нижний лист** для всех точек входа (допущение: ответ «Ок» на вопрос
   о формате трактован как согласие с концепцией листа).
2. Источники-конкуренты, НЕ попавшие в расчёт, **скрыты по умолчанию**; чекбокс
   «Показать неучтённые данные»; раскрытие/скрытие — **анимировано** (AnimatedSize,
   тайминг из дизайн-системы).
3. Карточка «Питание» — **три отдельные трассы**: калории / «Расход ≈» / «Баланс».
4. График энергобаланса — деталка **по конкретному дню** (вход из тултипа столбца).
5. Среднесуточные: таблица по дням; при сегменте 90 дней — **свёрнута** по умолчанию,
   при 7/30 — развёрнута.
6. EMA/темп: точки окна с сырыми весами + формула + правило разрыва; полная цепочка
   EMA — по кнопке «Показать все шаги EMA».
7. Настройки «Расход калорий»: трасса на **каждую строку-компонент** (BMR / Шаги /
   Силовые / Бытовой) и на «Итого сегодня».
8. Вес — в скоупе: тап по большому сглаженному числу на «Сегодня» → трасса EMA.

## 1. Принцип: трасса и цифра на экране — один код

- Среднесуточные (`avgSleepHours`, `avgSteps`, `avgCaloriesIn`, `avgMacros`,
  `avgExpenditure`) выносятся из VM в чистые функции домена, возвращающие значение
  И трассу; геттеры VM делегируют им и берут `.value`. Это устраняет текущее нарушение
  «VM без бизнес-логики» и гарантирует консистентность.
- Для остальных чисел (шаги/питание/расход/баланс за день, недел. энергостаты, темп,
  рекомендация, EMA) билдеры трасс читают те же кеши/модели/функции процессора.
- EMA-значения — только из существующего `computeEma`; недел. энергостаты — из
  `computeEnergyStats`; расход — из `computeExpenditures`/`ExpenditureDay`. Никаких
  повторных реализаций формул в билдерах.
- Регрессионные тесты: итог каждой трассы == значение соответствующего геттера/модели.

## 2. Домен: модели трассы

`lib/domain/calc_trace.dart` — НОВЫЙ, чистый Dart (без Flutter/Health), с
`==`/`hashCode` (паттерн остальных доменных моделей):

```dart
/// Откуда взято исходное число (бейдж в UI).
enum TraceSourceKind { healthConnect, manual, settings, formula, computed }

/// Одна строка секции «Исходные данные».
class TraceInput {
  final String label;        // «Шаги за 22 сентября»
  final String valueText;    // «12 400»
  final TraceSourceKind kind;
  final String? sourceName;  // «Samsung Health» (для healthConnect/manual)
  final String? recordsText; // «2 000 + 4 500 + 1 500» — записи источника
  final bool notUsed;        // true → конкурент, скрыт до чекбокса
  final String? notUsedReason; // «сумма меньше» / «меньше покрытие дней» / «источник отклонён»
}

/// Один шаг секции «Расчёт».
class TraceStep {
  final String title;        // «Суммируем записи победившего источника»
  final String? formulaText; // «2 000 + 4 500 + 1 500»
  final String? resultText;  // «= 8 000»
  final String? note;        // «агрегат HC не используется — резолюция по сырым точкам»
}

/// Строка таблицы «дата · значение · источник».
class TraceDayRow {
  final String dateText; final String valueText; final String? sourceName;
}

/// Строка цепочки EMA «дата · сырой вес · EMA» (+ флаг рестарта серии).
class TraceEmaRow {
  final String dateText; final double rawWeight; final double ema; final bool seriesRestart;
}

/// Готовая трасса для листа.
class CalcTrace {
  final String title;        // «Шаги»
  final String? subtitle;    // «22 сентября» / «окно 30 дней»
  final List<TraceInput> inputs;
  final List<TraceStep> steps;
  final String resultText;   // «8 000» — СТРОГО в формате экрана
  final String? resultUnit;  // «шагов»
  final String? resultNote;  // доп-итоги: «−0.7 кг за неделю», покрытие «по 41 дн.»
  final List<TraceDayRow>? dayRows;          // таблица среднесуточных (если есть)
  final bool dayRowsCollapsedByDefault;      // true при диапазоне 90
  final List<TraceEmaRow>? emaRows;          // цепочка EMA (темп/вес)
}
```

Форматирование чисел — в билдерах, по правилам экранов: `format.dart` (разделители
разрядов); вес — 1 знак; шаги — целые; ккал — паттерн движка `_formatKcal` (целое целым,
дробное — 1 знак); дельта — округление до 10; промежуточные значения — до 1 знака после
запятой. Итог трассы — СТРОГО как на экране (у `avgSteps` — `.round()`, у темпа —
`toStringAsFixed(1)` со знаком «−»/«+» и т.д.).

## 3. Домен: билдеры трасс (содержание каждой)

Новый файл `lib/domain/calc_trace_builders.dart` (чистые функции). Общий вход — кеши VM,
сырые точки сессии, `HealthDataProcessor`, `ExpenditureProfile`, `targetPace`, `today`,
диапазон. Данные конкурентов — через публичные хелперы процессора (§4), правила резолюции
не дублируются.

### 3.1 `stepsDayTrace(date)` — карточка «Шаги» («Сегодня», за вчера)

- Входы: записи победившего источника (по строке на точку либо строка-итог с
  `recordsText`); конкуренты: остальные источники дня (`notUsed: true`, причина «сумма
  меньше»); отклонённые («источник отклонён»); ручная запись (Tier 1) — «РУЧНОЙ ВВОД».
- Шаги: 1) правило «один источник на день»: Tier 1 → выбранный источник → «Авто»
  (максимальная сумма; показать сравнение `8 000 > 6 000`); 2) сумма записей победителя;
  примечание «агрегат HC не используется — резолюция по сырым точкам (Фаза 6 A2)».
- Итог: `N шагов` == `StepsDay.steps`.

### 3.2 `nutritionDayTrace(date)` — «Питание», калории

- Входы: записи победившего источника за день (ккал каждой в `recordsText`); Tier 1
  «Итог дня» — бейдж «РУЧНОЙ ВВОД». Конкуренты: прочие источники дня (`notUsed`,
  причина «меньше покрытие дней»).
- Шаги: 1) авто-правило источника: «по покрытию дней диапазона: A — 41 день, B — 12
  → A» (НЕ максимальная сумма; при равенстве — больше записей, затем большая сумма);
  2) «Итог дня» (Tier 1) побеждает при наличии; 3) сумма калорий победителя; макросы —
  сумма по записям, где есть; примечание «нет данных ≠ 0».
- Итог: `N ккал` == `NutritionDay.calories` (формат экрана), макросы в `resultNote`.

### 3.3 `expenditureDayTrace(date)` и `expenditureComponentTrace(date, component)`

Полная трасса 4 компонентов:

1. **BMR-каскад** — показать все уровни и где остановились: «ручной: не задан →
   HC BASAL за день: 1 670 ✓» либо «→ Mifflin: 10×84.2 + 6.25×178 − 5×36 + 5 = 1 752 ✓».
   Входы Mifflin: пол/год рождения (НАСТРОЙКИ), рост (ручной или HC-префилл — бейдж),
   возраст = год даты − год рождения (ФОРМУЛА), вес «на дату» + дата записи веса
   (бейдж источника). Если ни один уровень не сработал — трасса объясняет, почему
   расхода нет (профиль неполон / нет HC BASAL).
2. **Шаги**: `шаги_дня × вес_на_дату × коэффициент` с подстановкой; коэффициент из
   профиля (дефолт 0.0004) или пересчёт из оверрайда «ккал/1000 шагов»:
   `ккал/1000 ÷ вес ÷ 1000 = коэф.`; примечание «день без записи шагов = 0 шагов»;
   «нет веса на дату → компонент 0».
3. **Силовые**: «своя ккал/сессия × частота/7» ЛИБО `(MET − 1) × вес × часы × частота/7`
   с подстановкой всех параметров (MET 3.5/6.0 из интенсивности); «частота 0 → 0».
4. **Бытовой**: константа профиля.
5. **Сумма**: `bmr + шаги + силовые + быт`.

- Итог: `≈ N ккал/день` == `ExpenditureDay.total`.
- `expenditureComponentTrace(date, component)` — тот же билдер, в листе только один
  компонент (входы и шаги 1–4 соответственно) — для строк «Настроек».

### 3.4 `balanceDayTrace(date)` — «Баланс» (карточка питания; столбец графика)

- Входы: приход дня (значение + источник; «см. трассу калорий»), расход дня (значение;
  «см. трассу расхода»).
- Шаг: `приход − расход = ±N` (подстановка). Если расхода нет — объяснение «баланс не
  считается: BMR не рассчитан».
- Итог: `±N ккал` == `EnergyBalanceDay.balance`.
- Доп. строка (в `resultNote`): целевая линия графика `цель = вес × темп% × 11`
  (округление до 10) == `targetDeficitKcalPerDay`.

### 3.5 Среднесуточные (Тренд): `avgSleepTrace` / `avgStepsTrace` / `avgExpenditureTrace` /
`avgIntakeTrace` / `avgMacrosTrace`

Общая схема трассы:

1. Вход «окно»: сегмент 7/30/90 + примечание «“Сегодня” исключено — день не завершён».
2. Шаг «отсечение по разрыву»: правило «после последнего 5+-дневного пропуска своей
   метрики» (`daysAfterLastGap`, `gap_rule.dart`); показать количество отсечённых дней
   (например, «Отсечено 12 дней — правило 5+-дневного разрыва»).
3. Таблица `dayRows`: «дата · значение · источник» по дням, вошедшим в расчёт;
   `dayRowsCollapsedByDefault = (rangeDays == 90)`.
4. Шаг «сумма»: подстановка `a + b + … + z = S`.
5. Шаг «среднее»: `S / N = X`.
6. Итог: X (формат соответствующей ячейки) + покрытие «по N дн.» в `resultNote`.

Особенности по метрикам (знаменатели — только дни с данными своего типа):

- `avgStepsTrace` — итог `.round()` (как геттер); сон/шаги/… каждая метрика отсекается
  по СВОИМ дням с данными;
- `avgSleepTrace` — значения ночей `SleepDay.total` (asleep | deep+light+rem — как есть);
- `avgExpenditureTrace` — знаменатель «дни с рассчитанным BMR», значение `total`;
- `avgIntakeTrace` — знаменатель «дни с приходом» (покрытие == `intakeDaysInRange`);
- `avgMacrosTrace` — три суммы (Б/Ж/У) по одним и тем же дням; итоговая строка как на
  экране: `150 / 70 / 220 г`; примечание «день без макроса = 0».

Реализация: расчёт выносится из VM в функции `avgWithTrace(...)` (возвращают
`value + trace`), геттеры VM делегируют (§1). Для «сна» — аналогично из `avgSleepHours`.

### 3.6 `paceTrace()` — Темп (Саммари)

- Входы: `цель %/нед — НАСТРОЙКИ`; `допуск ±0.15 п.п. — ФОРМУЛА`; `EMA-период движка`
  (`RecommendationConfig.engineEmaPeriod`); `emaRows` = точки окна после отсечения
  (дата · сырой вес · EMA). Если EMA-точек после отсечения <5 — трасса-объяснение
  порога (итог «данных недостаточно»), без шагов расчёта.
- Шаги: 1) первая/последняя EMA-точки окна и дней между ними; 2)
  `rawPct = (EMAкон − EMAнач) / EMAнач × 100` с подстановкой; 3) нормализация
  `× 7 / дней`; 4) `кг за неделю = EMAкон − EMAнач`; 5) статус
  `|факт| против цель ± 0.15` (в темпе / слишком медленно / слишком быстро).
- Итог: `±X.X %/нед` == экран (`_paceValue`), в `resultNote` — `±N.N кг за неделю`.
- Кнопка «Показать все шаги EMA» (6, решение п. 2): полная цепочка текущей серии —
  каждая строка `EMA = (вес − EMAпрош) × k + EMAпрош`, `k = 2/(период+1)`; рестарты
  (5+ пустых дней) — строка «Разрыв — серия стартует заново». Значения — из
  `computeEma` (сравнение регрессионным тестом).

### 3.7 `energyWeekTrace()` — «Энергобаланс недели» (Саммари)

- Входы: окно `today−6 .. today−1` (6 дней). Таблица `dayRows` на день: приход ·
  расход · баланс; день без расхода — «баланс не считается» (правило A.4 п.4).
- Шаги: 1) средний приход = сумма / дни с приходом (подстановка); 2) средний расход =
  сумма / дни с BMR; 3) средний баланс = сумма / дни с приходом И расходом;
  4) ожидаемый темп = `avgBalance × 7 / 7700`.
- Итоги: 4 значения == `WeeklyEnergyStats` (avgIntake/avgExpenditure/avgBalance/
  expectedKgPerWeek), формат карточки «Энергобаланс недели».
- Значения — из `computeEnergyStats`; для таблицы дней при необходимости расширить
  `WeeklyEnergyStats` промежуточными данными (например, `List<EnergyDayRow>`) или
  добавить параллельную функцию в `weekly_energy_stats.dart` — решение при реализации,
  обязательное условие: значения не пересчитываются второй раз по другой логике.

### 3.8 `recommendationTrace()` — Рекомендация (Саммари)

- Входы: цель/факт темпа (ссылка: «из трассы темпа»), `avgIntake` (ссылка: «из
  энергобаланса недели»), вес (`вес на сегодня`, источник), коридор 50–300 и шаг 10.
- Шаги: 1) `дельта_raw = вес × |цель − факт| × 11` с подстановкой; 2) кламп 50–300 —
  показать до/после, если сработал; 3) округление до 10; 4)
  `intakeNew = intake ∓ дельта`; 5) подстановка в шаблон v2 — показать итоговый текст
  (какой шаблон выбран по статусу).
- Ветка без энергостатов (<2 дней с приходом): трасса объясняет, почему текст без
  чисел («данных питания <2 дней — тексты Фазы 5»), показывается использованный
  шаблон Фазы 5 с подстановками.
- Итог: текст рекомендации == `recommendationText` (посимвольно).

### 3.9 `smoothedWeightTrace()` — сглаженный вес («Сегодня», большое число)

- Входы: последнее взвешивание (значение/источник/дата), EMA-период отображения
  (3/5/10 — зависит от длины диапазона, `_emaPeriod`).
- Шаг: «сглаженный вес = последняя точка EMA-линии» + `emaRows` цепочки (свёрнуто,
  кнопка полной цепочки как в 3.6).
- Итог: `N кг` == `smoothedWeightToday` (1 знак после запятой).

## 4. Процессор: публичные данные о конкурентах (без дублирования правил)

`HealthDataProcessor` получает чистые функции-хелперы только для сбора отображаемых
данных (победителей по-прежнему определяют существующие `resolve*`):

- `Map<String, int> stepsSumsBySource(DateKey date, List<HealthDataPoint> points,
  {decisions, selection})` — сумма шагов за день по каждому источнику (для сравнения
  сумм в 3.1), включая отклонённые (с пометкой);
- `nutritionSourceStats(List<HealthDataPoint> points, {decisions, selection})` — по
  каждому источнику: покрыто дней / записей / сумма ккал (для 3.2);
- вес «на дату» и дата его записи — для 3.3 (значение из кеша + `WeightDay.date`).


## 5. ViewModel

Тонкие обёртки-билдеры (без бизнес-логики), пересчёт при каждом вызове (паттерн
`computeWeeklySummary`, U3):

```dart
CalcTrace stepsTraceFor(DateKey date);
CalcTrace nutritionTraceFor(DateKey date);            // калории
CalcTrace expenditureTraceFor(DateKey date);          // 4 компонента + итого
CalcTrace expenditureComponentTraceFor(DateKey date, ExpenditureComponent c);
CalcTrace balanceTraceFor(DateKey date);
CalcTrace avgSleepTrace();  CalcTrace avgStepsTrace();  CalcTrace avgExpenditureTrace();
CalcTrace avgIntakeTrace(); CalcTrace avgMacrosTrace();
CalcTrace paceTrace();  CalcTrace energyWeekTrace();
CalcTrace recommendationTrace();  CalcTrace smoothedWeightTrace();
```

Передают в билдеры кеши (`_weightCache`, `_stepsCache`, `_sleepCache`, `_nutritionCache`,
`_basalCache`, `_expenditureCache`), сырые точки сессии, `_decisions`/`_selections`,
`_energyProfile` (+HC-префилл роста), `_targetPace`, `today`, диапазон. Геттеры средних
делегируют `avgWithTrace` (§3.5) и возвращают `.value` — публичный API VM не меняется.

## 7. Тесты (ориентир +25–35 к текущим)

- Модели `calc_trace.dart`: `==`/`hashCode`, иммутабельность.
- Билдеры (фикстуры через мок-кеш): шаги с двумя источниками (конкурент скрыт,
  причина «сумма меньше»; отклонённый источник; Tier 1); питание (покрытие дней,
  Tier 1 «Итог дня», «нет данных ≠ 0»); расход (все ветки каскада BMR: manual/HC/
  Mifflin/ни одна; оверрайд ккал/1000 шагов; MET-ветка и своя сессия; частота 0;
  нет веса на дату); баланс (день без расхода); средние (разрыв 5+ дней — отсечённые
  дни; исключение «сегодня»; 90 дней → `dayRowsCollapsedByDefault`); темп (5 точек —
  считается; 4 — «данных недостаточно»; рестарт EMA в цепочке); энергобаланс недели
  (день без расхода в таблице); рекомендация (кламп дельты 50/300, округление до 10,
  ветка без энергостатов); EMA-число == `smoothedWeightToday`.
- Регрессия консистентности: для каждой трассы `trace.resultText` == значение
  соответствующего геттера/модели (все средние, расход, баланс, энергостаты, темп).
- Виджет-тесты листа: чекбокс переключает блок конкурентов; таблица свёрнута при
  `collapsedByDefault`; кнопка EMA разворачивает цепочку.
