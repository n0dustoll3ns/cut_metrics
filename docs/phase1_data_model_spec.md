# Cut Metrics — Фаза 1: модель данных и приоритет источников

> ТЗ для разработки. Ссылается на `cut_metrics_project_map.md` (актуальное состояние кода на 2026-06-29).
> Статус: к реализации.

---

## 1. Контекст

Сейчас в `HealthDataProcessor` три метрики мёржатся тремя разными случайными правилами:

| Метрика | Текущее правило | Проблема |
|---|---|---|
| Вес | `mergeWeightInto()` — last-wins по времени записи | Нет понятия "источник", просто последняя по времени запись побеждает |
| Шаги | `mergeStepsInto()` — суммирование всех записей за день | Если появится 2-й источник (наш ручной ввод), данные задвоятся |
| Питание | `mergeNutritionInto()` — первое вхождение | Вне скоупа этой фазы |

Цель фазы: ввести единую модель **приоритета источников на дату**, куда наше приложение (ручной ввод) добавляется как ещё один источник — с гарантией, что ручная правка пользователя всегда выигрывает, если она есть.

---

## 2. Скоуп

**В скоупе:** Weight, Steps.
**Вне скоупа:** Nutrition/КБЖУ (по бизнес-решению — не трогаем на этом этапе), Sleep (ручной ввод сна не планируется, `SleepAnalyzer` не меняется).
**Не входит в эту фазу:** сам механизм записи в Health Connect и permissions (→ Фаза 2), UI подтверждения "ок/не ок" (→ Фаза 3). Здесь фиксируется только модель данных и алгоритм резолюции, а также **интерфейсный контракт**, который Фаза 2 должна реализовать.

---

## 3. Термины

- **Tier 1** — запись, у которой `dataOrigin` = пакет нашего приложения (ручной ввод пользователя через Cut Metrics).
- **Tier 2** — любые внешние записи (умные весы, шагомер телефона, другие приложения).
- **Resolved value** — итоговое значение метрики на дату после применения приоритета Tier 1 → Tier 2.

## 5. Алгоритм резолюции

Заменяет `mergeWeightInto()` и `mergeStepsInto()`.

### 5.1 Вес — `resolveWeightForDate(date)`

1. Есть запись с `dataOrigin` = наш пакет на эту дату? → вернуть `WeightDay(source: manual)`. Готово.
2. Иначе — среди внешних записей применить **текущее** правило last-wins по времени записи (без изменений, регресса нет). Вернуть `WeightDay(source: external)`.
3. Записей нет вообще → вернуть `null` (Фаза 3 решает, что показать — блокирующий ввод).

**Примечание:** вес — не кумулятивный тип, платформенного `aggregate()`-механизма приоритета для него нет (в отличие от шагов, см. ниже). Если в будущем понадобится более явный приоритет между несколькими внешними весами (например "умные весы важнее ручной оценки в другом приложении") — это отдельное решение, не блокирует эту фазу.

### 5.2 Шаги — `resolveStepsForDate(date)`

1. Есть запись с `dataOrigin` = наш пакет на эту дату? → вернуть `StepsDay(source: manual)`. **Все остальные внешние записи на эту дату полностью игнорируются** — это единственный способ гарантировать, что правка пользователя побеждает, поскольку приоритетами между внешними источниками в Health Connect управляет только сам пользователь через системные настройки, не наш код.
2. Ручной записи нет → использовать `aggregate()` (`AggregateGroupByPeriod` / `COUNT_TOTAL` за день) **вместо** `readRecords()` + суммирования. Это и есть "выбрать один источник по приоритету, не складывать" — но приоритет между внешними источниками здесь определяет пользователь в настройках Health Connect ("Источники данных и приоритет"), а не наше приложение. Мы гарантируем только отсутствие задвоения.
3. `aggregate()` вернул 0/null → нет данных, Фаза 3 показывает блокирующий ввод.

## 6. Отмена ручной коррекции

Требование подтверждено: отмена нужна сразу.

- Контракт репозитория включает `deleteManualRecord(date, metricType)`.
- После удаления специальной логики "отката" не требуется — при следующем вызове `resolveWeightForDate`/`resolveStepsForDate` шаг 1 просто не находит ручную запись и алгоритм естественным образом попадает в Tier 2. Это встроенное свойство такой архитектуры, а не отдельная фича.

## 7. Интерфейсный контракт для Фазы 2

Фаза 1 не реализует запись, но резолюция зависит от следующих методов репозитория — их сигнатуры фиксируются здесь, реализация в Фазе 2:

```dart
abstract class HealthRepository {
  Future<bool> hasManualRecord(DateKey date, MetricType type);
  Future<void> writeManualRecord(DateKey date, MetricType type, num value);
  Future<void> deleteManualRecord(DateKey date, MetricType type);

  // Существующий метод, без изменений — используется для веса (Tier 2)
  Future<List<HealthDataPoint>> fetchRawData({required List<HealthDataType> types, required DateTime startDate, required DateTime endDate});

  // НОВЫЙ — используется для шагов (Tier 2), заменяет суммирование сырых записей
  Future<int?> aggregateExternalSteps(DateKey date);
}
```
