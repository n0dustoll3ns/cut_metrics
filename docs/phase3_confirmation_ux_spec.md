# Cut Metrics — Фаза 3: UX-поток подтверждения значения

> ТЗ для разработки. Опирается на контракты из `cut_metrics_phase1_data_model_spec.md`
> (резолюция по приоритету) и `cut_metrics_phase2_repository_write_spec.md` (запись/удаление).
> Визуальное оформление (беджи, цвета, конкретные виджеты) — предмет Фазы 5, здесь не решается.

---

## 1. Контекст и цель

Флоу, зафиксированный ранее: данные показываются сразу, рядом — контрол "ок/не ок"; "не ок"
раскрывает ручной ввод; отсутствие данных — обязательный ввод. Эта фаза описывает состояния,
переходы между ними и то, как это подключается к `ViewModel`, `HealthRepository` (Фаза 2) и
алгоритму резолюции (Фаза 1).

---

## 2. Скоуп

- Метрики: вес, шаги (как и в предыдущих фазах).
- **Доступность: любая дата, включая историю** — не только текущий день.
- Блокировка при отсутствии данных — **только карточка конкретной метрики**, остальной экран
  остаётся полностью доступен.
- Вне скоупа: Nutrition, Sleep; визуальное оформление (Фаза 5).

---

## 3. Состояния карточки метрики на дату

Для пары (дата, тип метрики) — пять состояний:

| Состояние | Условие входа | Что видит пользователь |
|---|---|---|
| `loading` | Идёт резолюция (Фаза 1) | Скелетон/спиннер |
| `missing` | Резолюция вернула `null` | Обязательный ввод, **блокирует только эту карточку** |
| `autoUnconfirmed` | `source == external` | Значение + контрол "ок / не ок" |
| `manualEntryActive` | Нажали "не ок" ИЛИ были в `missing` | Поле ввода активно |
| `manualConfirmed` | `source == manual` | Значение + контрол "отменить" |

---

## 4. Переходы

```
loading ──(резолюция)──> missing | autoUnconfirmed | manualConfirmed

missing ──(тап "ввести")──> manualEntryActive
autoUnconfirmed ──(тап "не ок")──> manualEntryActive
autoUnconfirmed ──(тап "ок")──> autoUnconfirmed (см. п.5 — без побочных эффектов)

manualEntryActive ──(submit)──> writeManualRecord() ──> manualConfirmed
manualEntryActive ──(отмена ввода, не сохраняя)──> предыдущее состояние (missing | autoUnconfirmed)

manualConfirmed ──(тап "отменить")──> deleteManualRecord() ──> missing | autoUnconfirmed
                                       (естественный откат на Tier 2, см. Фазу 1, п.6 —
                                       дополнительной логики отката не требуется)
```

---

## 5. "Ок" не имеет побочных эффектов — важно для согласованности

Тап "ок" **не вызывает никаких методов записи**. Это чисто UI-подтверждение (можно дать лёгкую
визуальную реакцию — например, короткую анимацию), но никакого состояния никуда не пишется.

Это не отдельное решение, а следствие уже принятого: в Фазе 4 мы отказались от локального кэша —
если бы "ок" нужно было где-то запоминать, это потребовало бы хранилища, которого нет. Раз "ок" не
пишет ничего — при каждой новой загрузке карточка снова покажет `autoUnconfirmed` для этой даты,
и это ожидаемо: контрол всегда доступен, а не "запоминает" что его уже нажимали.

---

## 6. Точки входа в детали дня

- **Тап по точке графика** (`LineChart` для веса+EMA, `BarChart` для шагов в `DashboardView`) —
  открывает состояние для тапнутой даты. `fl_chart` (уже в зависимостях, см. project map) даёт
  точечные touch-колбэки (`lineTouchData`/`barTouchData`) для определения, какая именно точка
  тапнута — новая зависимость не нужна.
- **Экран "Сегодня"** — для текущей даты контрол встроен по умолчанию, без необходимости тапать
  по графику (это самый частый кейс использования).

---

## 7. Побочный эффект правки исторической даты на EMA

**Вес:** EMA — скользящее среднее, зависит от последовательности предыдущих значений. Правка
веса за прошлую дату меняет EMA для всех дат **после** неё в загруженном диапазоне. После
`submitManualValue`/`cancelManualValue` для веса — триггерить тот же путь пересчёта, что уже
используется в `computeEma()` при `setDate()` (полный пересчёт по кешу). Это не самый быстрый
вариант (см. известный TODO из project map о производительности при данных за год+), но
корректный — оптимизация пересчёта отдельно, не задача этой фазы.

**Шаги:** не накопительны в этом смысле — правка одной даты не влияет на соседние даты, пересчёт
не нужен.

## 8. Контракт ViewModel (добавления)

```dart
// Уже резолвленное (Фаза 1) значение + источник для конкретной даты.
// Новых обращений к Health Connect не требует — значение уже в существующих
// кешах (_weightCache/_stepsCache), это чтение по ключу.
ResolvedValue<T>? getResolvedValue<T>(DateKey date, MetricType type);

// Пишет ручное значение (→ Фаза 2), обновляет кеш для этой даты,
// при необходимости пересчитывает EMA (п.7), notifyListeners().
Future<void> submitManualValue(DateKey date, MetricType type, num value);

// Удаляет ручную запись (→ Фаза 2), откатывает на Tier 2/missing,
// обновляет кеш, пересчитывает EMA при необходимости, notifyListeners().
Future<void> cancelManualValue(DateKey date, MetricType type);
```
