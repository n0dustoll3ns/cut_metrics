## Часть A — RecommendationEngine

### A.1 Контекст и цель

Ядро ценности продукта: сравнение фактического темпа изменения веса с целевым, определение
статуса, формирование текста рекомендации. Чистый Dart-модуль, без зависимостей от Flutter/UI —
как и зафиксировано в исходной архитектуре.

### A.2 Входные данные

- EMA-сглаженный вес за период — из существующего `computeEma()`.
  ⚠️ **Важно:** сейчас `_emaPeriod` в `ViewModel` — 3/5/10 дней в зависимости от длины
  просматриваемого диапазона (это настройка отображения графика). `RecommendationEngine` не должен
  зависеть от этого — ему нужен **свой фиксированный** период сглаживания, не завязанный на то,
  какой диапазон пользователь сейчас листает на дашборде. Значение периода — отдельный параметр
  конфигурации движка, не переиспользует `_emaPeriod`.
- Целевой темп пользователя (0.3–1.4%/нед, один из 2–3 пресетов) — новая небольшая настройка,
  h比е БД (см. Фазу 4, п.3) — хранится через `shared_preferences` или аналог.
- Дата последнего показанного саммари — для определения готовности нового цикла.

### A.3 Алгоритм

1. `weeklyRange` — последние 7 дней относительно текущей даты (скользящее окно, не привязанное
   к дню недели онбординга — простейший вариант, соответствует принципу минимума инжиниринга).
2. `actualPacePercent = (EMA(range.end) − EMA(range.start)) / EMA(range.start) × 100`
3. Статус — сравнение `|actualPacePercent|` с целевым `targetPacePercent` с учётом допуска:
   - `|actual − target| ≤ tolerance` → `PaceStatus.inPace`
   - `actual` меньше цели по модулю → `PaceStatus.tooSlow` → рекомендация снизить калорийность
   - `actual` больше цели по модулю → `PaceStatus.tooFast` → рекомендация повысить калорийность /
     рефид (сама логика рефида не реализуется — открытый вопрос из бизнес-документа, раздел 3;
     здесь только шаблонный текст-заглушка)
4. Текст саммари — статус + 1–2 шаблонных предложения (не ИИ-генерация, простые строковые шаблоны
   с подстановкой чисел).

### A.4 ⚠️ Открытый параметр: величина допуска (tolerance)

Ни в бизнес-документе, ни где-либо ещё не зафиксировано конкретное число для "фактический темп
близок к целевому". Предлагаю **±0.15 п.п.** как отправную точку (если цель 0.8%, то 0.65–0.95%
считается "в темпе") — но это моё предположение, не решение из ТЗ. Это дешёвый параметр для
последующей правки (одна константа), поэтому не блокирую фазу, но явно фиксирую, что число не
подтверждено тобой.

### A.5 Пресеты целевого темпа (предположение, требует подтверждения)

Бизнес-документ описывает диапазон 0.3–1.4% и "2–3 скорости", но не называет точные числа.
Предлагаю три пресета, равномерно внутри диапазона:

| Пресет | Значение |
|---|---|
| Бережный | 0.4% |
| Стандартный | 0.8% |
| Агрессивный | 1.2% |

Поправь, если у тебя уже есть конкретные числа — это конфигурационный список, не архитектурное
решение, меняется без последствий для остального кода.

### A.6 Еженедельный цикл

```dart
bool isSummaryDue(DateTime today, DateTime lastSummaryDate) =>
    today.difference(lastSummaryDate).inDays >= 7;
```

После показа саммари — `lastSummaryDate = today`, сохраняется в тех же настройках, что и целевой
темп (не отдельное хранилище).

### A.7 Выходная модель

```dart
enum PaceStatus { inPace, tooSlow, tooFast }

class WeeklySummary {
  final DateTimeRange range;
  final double actualPacePercent;
  final double targetPacePercent;
  final PaceStatus status;
  final String recommendationText;
}
```

### A.8 Definition of Done (часть A)

- [ ] `RecommendationEngine` — чистый Dart-класс/функция без импортов Flutter/Health Connect
- [ ] Собственный фиксированный период EMA, не связанный с `_emaPeriod` дашборда
- [ ] Реализован алгоритм статуса (A.3) с параметризуемым `tolerance` (не хардкод в теле метода)
- [ ] Пресеты темпа — конфигурируемый список, а не 3 захардкоженных числа внутри логики
- [ ] `isSummaryDue`/`lastSummaryDate` реализованы, хранятся через `shared_preferences`
- [ ] Юнит-тесты на все три статуса + границы допуска (ровно на границе tolerance)

### B.2 CSS — расширение существующего `.badge` (не новый компонент)

Файл уже определяет `.badge-steady`/`.badge-alert` для статуса темпа — по той же схеме (точка +
текст Deep Ink на бледной подложке, не сплошная заливка — как явно обосновано в файле про AA-контраст):

```css
.badge-source-auto{
  background:var(--surface-2); border-color:var(--outline); color:var(--ink-muted);
}
.badge-source-auto .badge-dot{ background:var(--noise); }

.badge-source-manual{
  background:var(--signal-tint); border-color:var(--outline); color:var(--ink);
}
.badge-source-manual .badge-dot{ background:var(--signal); }
```

`--signal-tint` (`#E7EEF8`) уже определён в файле как "derived signal tone для состояний" —
переиспользуется как есть. `--surface-2`/`--outline` — существующие M3-нейтрали, не новые токены.
