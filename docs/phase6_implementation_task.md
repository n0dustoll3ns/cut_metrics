## 2. Часть A — багфиксы из отчёта

### A0. Диагностика (DebugLog с устройства)

Не блокирует разработку, но ускоряет A1. Сценарий для пользователя:

1. Открыть приложение → «Сегодня».
2. Вес: «Не ок» → ввести значение → галочка. Шаги: «Ввести» → значение → галочка.
3. Настройки → 5 тапов по подписи версии → «Копировать всё» → прислать лог.

Смотреть тег `repo`: `writeManualRecord … вернул false`, `hasManualRecord … sourceId=[…],
наш пакет=… → …`, `aggregateExternalStepsForRange: N дней с шагами`.

**Итоги A0-лога** (получен от пользователя 2026-09-02, `memory-bank/debug.log`):

1. Все permissions выданы; `writeManualRecord` для веса и шагов возвращает **OK** —
   A1.4 (корректировка параметров записи) не требуется.
2. **`sourceId` пуст у всех точек** («источники: —» во всех `fetchRawData`), включая
   наши только что записанные. Причина найдена в исходниках пакета `health` 13.3.1/13.3.2:
   `HealthDataConverter.createBaseRecord` (Android/Kotlin) отдаёт захардкоженный
   `"source_id" to ""` для WEIGHT/STEPS и почти всех типов (заполнен только у sleep-сессий);
   реальный пакет приложения приходит в **`source_name`** = `metadata.dataOrigin.packageName`.
   Следствие: Tier 1 и список источников (C.1) строить по `sourceName` (Android),
   `sourceId` оставить как fallback (iOS/будущие версии). Запланированный fallback-детект
   «новый sourceId после записи» (A1.2) не нужен — наш пакет распознаётся напрямую по
   `sourceName == appPackageId`; ключ `our_source_id` не требуется.
3. `aggregateExternalStepsForRange` (getHealthIntervalDataFromTypes, interval=1440) →
   «0 дней с шагами» при 24 587 сырых точках STEPS — техриск №4 подтверждён, решение A2
   (резолюция шагов по сырым точкам) верное. `getTotalStepsInInterval` → 11 758 (работает,
   но уходит из архитектуры).
4. DebugLog доработать (требование пользователя, 2026-09-02): логировать нажатия
   «Ок»/«Не ок» для веса И шагов (сейчас эти действия в лог не попадают вообще);
   в сообщения `repo` включать `sourceName` точек, а не только `sourceId`.
5. Служебное: `load` — 4.2 с (STEPS: 24 587 точек ≈ 2.9 с) — заметка на будущее, не блокирует.

### A1. Ручной ввод не побеждает внешние данные (вес и шаги) — техриск №1

Симптомы из отчёта: у веса «Не ок» → ввод → галочка «ничего не меняет»; у шагов после
ввода показывается значение из Health. Наиболее вероятная причина: Tier 1 определяется
сравнением `p.sourceId == appPackageId` (`health_data_processor.dart`); если фактический
`sourceId` записей нашего приложения на устройстве отличается от package name — ручная
запись никогда не распознаётся, всегда побеждает Tier 2.

Фиксы:

1. **Идемпотентность записи**: `submitManualValue` = `deleteManualRecord(date, type)`
   (наши записи за день) → `writeManualRecord` → `_reloadDate`. Устраняет накопление
   дублей (сейчас каждый повторный submit дописывает новую запись в Health Connect).
2. **Fallback-детект своего sourceId** (защита от несовпадения): после первой успешной
   записи прочитать точки дня — sourceId, которого не было до записи, наш. Закешировать
   в `SettingsService` (ключ `our_source_id`), использовать в Tier 1 наравне с
   package name. Применяется и в `deleteManualRecord` (наши записи = оба id).
3. **Видимый фидбек ошибки**: неудачный write — снекбар прямо на карточке («Не удалось
   сохранить»), а не только ErrorBox внизу экрана (его легко не заметить — отчёт это
   подтвердил).
4. По логу из A0: если `writeHealthData` возвращает false — скорректировать параметры
   записи (например, `endTime` для WEIGHT) по фактическому поведению Health Connect.

### A2. Шаги из Health не отображаются — техриск №4

Симптом: шагов на «Сегодня» нет, но после ручного ввода показывается значение из Health.
Значит: `getHealthIntervalDataFromTypes(interval: 1440)` данных не даёт (техриск №4
подтвердился), а `getTotalStepsInInterval` работает.

Решение — убрать зависимость шагов от обоих aggregate-API: **резолюция шагов из сырых
точек** `fetchRawData(STEPS)` по правилу «один источник на день» (см. C.2):

- выбран источник — сумма его точек за день;
- «Авто» — источник с максимальной суммой за день среди неотклонённых.

`aggregateExternalStepsForRange` и `aggregateExternalSteps` удаляются из контракта
репозитория и резолюции — техриски №2/№4 закрыты архитектурно. Батчевость сохраняется:
один `fetchRawData` на диапазон, как для веса (Фаза 4, DoD 3 не нарушается).

### A3. Даты на графике

Реализовать паттерн из задания №1 §5 в `WeightChart` (общий для «Сегодня» и «Тренда»):
число дня; «1 АВГ» на границе месяца (Ink Muted, показывается всегда, вытесняет
соседнюю); прореживание ≤8 меток (шаг = ceil(точек/7)); тонкая вертикальная линия сетки
на границе месяца; тултип с полной датой.

### A4. «Ок ничего не меняет» (вес)

По Фазе 3 §5 — осознанное поведение (снекбар на 1 сек). Меняется в части B: «Ок» теперь
запоминает решение и переводит карточку в тихий режим. Мгновенный снекбар остаётся.

## 3. Часть B — кеш подтверждений «Ок/Не ок»

### B.1. Модель

- `ConfirmDecision { none, confirmed, refused }` — новый файл `lib/domain/confirm_decision.dart`.
- Ключ решения — пара (MetricType, sourcePackage).
- `confirmed` — карточка тихая (autoConfirmed), крупные «Ок/Не ок» не показываются.
- `refused` — данные этого источника по этой метрике исключаются из резолюции; карточка
  переходит в режим ручного ввода (sourceRefused).
- Источник без решения (в т.ч. впервые появившийся) — снова autoUnconfirmed.

### B.2. Хранение

`SettingsService`, ключ `src_decision.<metric>.<package>` = `confirmed|refused`
(отсутствие ключа = none). Это пользовательская настройка в рамках исключения
Фазы 4 §3 (НЕ данные здоровья) — добавить примечание в `phase4_no_cache_spec_v2.md`
(секция «Изменения Фазы 6»).

### B.3. ViewModel

- Хранить сырые точки сессии (`_rawWeightPoints`, `_rawStepsPoints`) — смена решения или
  выбранного источника перерезолвит из памяти, без похода в Health Connect.
- `getResolvedValue` дополнительно возвращает `sourcePackage` (для бейджа и решения).
- Новые методы: `confirmSource(metric, package)`, `refuseSource(metric, package)`,
  `resetDecision(metric, package)` — обновляют настройку и перерезолвляют кеши.
- Резолюция учитывает решения (см. C.2).

### B.4. UI

- Карточка: состояния по заданию №1 §7; меню «⋯»; снекбар при отказе источника.
- «Ок» теперь ПИШЕТ решение (но по-прежнему не пишет данных) — тест Фазы 3
  «"Ок" не вызывает writeManualRecord» обновить: не пишет данные, пишет решение.
- В `phase3_confirmation_ux_spec.md` добавить секцию «Изменения Фазы 6».

## 4. Часть C — выбор источника данных

### C.1. Модель и хранение

- `SourceSelection { auto, app(String package) }` — новый файл
  `lib/domain/source_selection.dart`; на метрику (вес, шаги).
- Ключ `src_selection.<metric>` в `SettingsService`, дефолт `auto`.
- Список найденных источников — уникальные `sourceId` сырых точек сессии (без
  дополнительных запросов к HC). Наш пакет в список не входит — Tier 1 всегда побеждает.

### C.2. Резолюция (обновлённая, для веса и шагов)

Tier 1 (наш пакет) всегда побеждает — Фаза 1, без изменений (учитывая fallback-детект
sourceId из A1). Tier 2:

1. Отбрасываются источники с решением `refused`.
2. Выбрано приложение — только его точки.
3. «Авто»: вес — last-wins по `dateFrom` (как сейчас); шаги — источник с максимальной
   суммой за день (замена aggregate, A2); если в дне несколько источников — warn в
   DebugLog (диагностика выбора).
4. Пригодных точек нет → `missing`.

`WeightDay`/`StepsDay` расширяются полем `sourcePackage` (обновить `==`/`hashCode`
и тесты) — бедж и решения работают с конкретным приложением.

### C.3. Имена источников

`lib/services/source_names.dart`: словарь package → отображаемое имя (Google Fit,
Samsung Health, Mi Fitness, Fitbit, Withings, Garmin Connect, Huawei Health, Polar Flow
и т.п. — пополняется просто); fallback — последний сегмент пакета; неопределённый
package — «Health Connect».

### C.4. UI

- Настройки → «Источники данных Health Connect» → подэкран выбора (задание №1 §8):
  радио «Авто» + найденные приложения со статусом решения; сброс решения; отклонённый
  источник выбрать нельзя.
- Смена выбора — перерезолюция из сессионных сырых точек + `notifyListeners`.
- Выбор конкретного источника означает доверие: карточка не спрашивает «Ок/Не ок».
