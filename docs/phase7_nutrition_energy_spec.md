## 1. Контекст и цель

Пользователь уже ведёт трекер питания (предпосылка продукта) — с Фазы 7 приложение читает эти
данные из Health Connect и впервые замыкает **энергобаланс**: приход (КБЖУ) против расхода
(BMR + шаги + силовые + бытовой). Баланс связывается с ядром продукта — целевым темпом — через
линию целевого дефицита на графике и энергоблок еженедельного саммари.

Коммерческие рамки (без paywall-логики): график баланса и карточки — бесплатные хуки ежедневного
удержания; энергоблок саммари и конкретные рекомендации в ккал — усиление будущего платного ядра.

Почему расход считается собственной моделью, а не `TOTAL_CALORIES_BURNED`: показания вендоров
систематически завышены (профильные BMR-формулы + пульсометрия силовых + адаптивный термогенез —
разбор в чате аналитики 2026-09-10); собственная декомпозиция прозрачна, калибруема и согласована
с физикой тренда веса. Доверять готовым цифрам расхода будем в Фазе 8 (там же сравнение моделей).

## 2. Границы скоупа

**В скоупе:** чтение NUTRITION и BASAL_ENERGY_BURNED, модель расхода из 4 компонентов, ручной
оверрайд всех компонентов, ручная запись «Итог дня», график A2, карточка «Питание» на «Сегодня»,
среднесуточные на Тренде, энергоблок саммари + RecommendationEngine v2, ленивый ввод профиля.

**Вне скоупа:** рефиды и адаптивный TDEE («ожидание vs факт») — Фаза 8; индикатор белка — бэклог
(раздел 12); `TOTAL_CALORIES_BURNED` / `ACTIVE_ENERGY_BURNED` — не используем; paywall/AccessGate;
iOS; чтение WORKOUT (силовые — только параметры пользователя).

## 3. Часть A — домен: питание и расчёт расхода

### A.1 Модель `NutritionDay`

```dart
class NutritionDay {
  final DateKey date;
  final double calories;              // ккал, сумма за день
  final double? protein, fat, carbs;  // г; null, если источник не отдаёт макросы
  final DataSource source;            // manual | external (как WeightDay/StepsDay)
  final String? sourcePackage;        // dataOrigin победившего источника
}
```

+ `==`/`hashCode` по всем полям. `MetricType` расширяется значением `nutrition` — механика
решений/выбора источника Фазы 6 (B/C) переиспользуется автоматически (ключи
`src_decision.nutrition.<pkg>`, `src_selection.nutrition`; цикл загрузки в `load()` уже итерирует
`MetricType.values`).

### A.2 Профиль расхода и настройки

### A.3 Формулы и константы — `lib/domain/expenditure_config.dart`

Все константы Фазы 7 в одном месте (паттерн `RecommendationConfig` Фазы 5):

- **BMR (Mifflin-St Jeor):** М: `10W + 6.25H − 5A + 5`; Ж: `10W + 6.25H − 5A − 161`
  (W — кг, H — см, A — полных лет). Вес — последний резолвленный на дату или ранее (A.5).
  Обоснование: Frankenfield et al. 2005 (J Am Diet Assoc) — точнее Harris-Benedict; стандарт
  первого выбора Американской диетологической ассоциации, когда состав тела неизвестен.
- **Шаги (нетто-стоимость ходьбы):** `kcal = шаги × вес × 0.0004`.
  Обоснование: чистая стоимость ходьбы по ровному ≈ 0.45–0.5 ккал/кг/км (Margaria); gross-оценка
  ACSM ≈ 0.65–0.7 ккал/кг/км. **Нетто — обязательно**: BMR теперь отдельный компонент за полные
  сутки, gross давал бы задвоение ~100–150 ккал/день. Прежний коэффициент 0.0005 (gross-эквивалент)
  был корректен, когда BMR не считался вовсе.
- **Силовые (Compendium of Physical Activities, Ainsworth 2011):**
  `kcal_сессия = (MET − 1) × вес × часы`; MET = 3.5 (умеренная, код 02050) / 6.0 (тяжёлая, 02060);
  нетто (−1 MET) — та же причина. Дневная добавка = `kcal_сессия × частота / 7`.
- **Бытовой:** 200 ккал/день — TEF (~10% рациона) + мелкая активность сверх учтённых шагов;
  литературный коридор для сидячих 150–300.
- **Целевой дефицит:** `ккал/день = вес × темп(%) × 11` (7700 ккал/кг ÷ 7 дней ÷ 100).
  Пример: 70 кг × 0.8% → −616 ккал/день.

### A.4 Каскад BMR на день

1. Ручной оверрайд (`energy_bmr_mode = manual`) → константа на все дни.
2. HC `BASAL_ENERGY_BURNED`: instant-записи, значение в **ккал/день** (`HealthDataConverter.kt:78`
   пакета health 13.3.2, `inKilocaloriesPerDay`), last-wins за день.
3. Формула Mifflin-St Jeor — заполняет дни без HC-записей, если профиль полон
   (пол + возраст + рост + известен вес на дату).
4. Ничего → расход за день «—», баланс за день не считается.

### A.5 `ExpenditureDay` — расчёт расхода по дням

```dart
class ExpenditureDay {
  final DateKey date;
  final double bmrKcal;       // каскад A.4
  final double stepsKcal;     // шаги_дня × вес_на_дату × 0.0004
  final double trainingKcal;  // (MET−1) × вес × часы × частота / 7
  final double householdKcal; // 200 (или оверрайд)
  double get total => bmrKcal + stepsKcal + trainingKcal + householdKcal;
}

class EnergyBalanceDay {
  final NutritionDay intake;
  final ExpenditureDay out;
  double get balance => intake.calories − out.total;
}
```

Считается синхронно в процессоре из резолвленных кешей (без хранения сырых точек). Вес «на дату» —
последняя резолвленная запись веса ≤ дата (префикс-проход по сортированному кешу). День без записи
шагов = 0 шагов (текущая семантика сохраняется).

### A.6 Резолюция питания — «один источник на день»

Паттерн Фазы 6 A2/C с одним принципиальным отличием:

- **Авто-правило НЕ «максимальная сумма»** (для калорий оно систематически выбирало бы самый
  завышающий источник — см. аналитику о достоверности расхода). Авто = источник с **наибольшим
  числом дней, имеющих записи**, в загруженном диапазоне; при равенстве — больше записей; при
  равенстве — большая сумма калорий. Несколько источников в дне → warn в DebugLog
  (`onWarn`-паттерн процессора).
- Ценность дня = **сумма калорий и макросов только победившего источника** (записи внутри дня
  суммируются — трекеры пишут по пункту/приёму пищи).
- Tier 1: наш «Итог дня» всегда побеждает для своей даты; refused-фильтр и выбор источника — как
  у шагов (Фаза 6 B/C, `MetricType.nutrition`).
- День без записей = «нет данных» → исключается из всех средних; показывается покрытие
  «по N из M дней».

### A.7 Ручная запись «Итог дня» (Tier 1)

- Контракт репозитория: `writeManualNutrition(DateKey date, {required double calories,
  double? protein, double? fat, double? carbs})` + `hasManualNutrition(DateKey)` +
  `deleteManualNutrition(DateKey)`.
- Реализация через `Health.writeMeal` (пакет `health` 13.3.2, `health_plugin.dart:961`):
  `mealType: MealType.UNKNOWN`, **`name: 'Итог дня'` (обязательно непустое — HC требует имя у
  NutritionRecord)**, `startTime/endTime` = границы суток (`DateKey.startOfDay`/`endOfDay`),
  `recordingMethod: RecordingMethod.manual`.
- Идемпотентность: delete-then-write наших NutritionRecord за дату (аналог A1.1 Фазы 6).
- Общий `writeManualRecord(num value)` веса/шагов не меняется.

### A.8 Правило «сегодня»

`Today = DateKey(DateTime.now())` исключается из: средних прихода/расхода/баланса на Тренде,
энергостатов саммари (C.1), avgSteps (семантика «подсчёт не завершён»). Вес: запись за сегодня
делает день валидным для веса, графиков и данных веса. График баланса включает столбец «сегодня»
(данные дня ещё не полные — осознанно, без спец-пометки).

## 4. Часть B — экраны

### B.1 График энергобаланса («Тренд», под графиком веса)

- `EnergyBalanceChart` (`lib/ui/energy_balance_chart.dart`), fl_chart `BarChart`: один столбец на
  день = `баланс` (приход − расход), **отрицательные — вниз от нулевой линии** (дефицит).
- Цвета: дефицит — `steady` (зелёный), профицит — `alert` (ржавый); **новых hex не вводить**

- Тултип: «17 июл · Приход 2150 · Расход 2680 · Баланс −530».
- Дни без данных о приходе — столбца нет; под графиком примечание «Дней без данных питания: N».
- Ось дат — переиспользовать механику WeightChart A3 (числа, «1 АВГ» на границе месяца, ≤8 меток).
- Заголовок/легенда: «Энергобаланс · ккал/день» + легенда (столбец дефицита/профицита, целевая линия).

### B.2 Карточка «Питание» («Сегодня», после кнопки саммари)

| Состояние | Вид |
|---|---|
| `loading` | скелетон |

### B.3 «Среднесуточные показатели» на Тренде

- «АКТИВНОСТЬ» заменяется на **«РАСХОД»** — полный расход из 4 компонентов (семантика меняется с
  «активность» на TDEE-подобную; отметить в заметках к сборке).
- Добавляется ячейка **«ПРИХОД»** (ккал/день по дням с данными; «—» при отсутствии).
- Вторая компактная строка **Б / Ж / У** (средние граммы по дням с данными).
- Все средние исключают «сегодня» (A.8); покрытие — подпись «по N дням» мелким кэпшеном.

### B.4 Настройки

Новый блок **«Профиль расхода»** (после целевого темпа): пол (м/ж), год рождения, рост (префилл из
HC `HEIGHT`, ручная правка). Если профиль неполон и HC-BMR недоступен — строка-подсказка.

Новый блок **«Расход калорий»**: 4 строки-компонента, у каждой источник (HC/формула/дефолт) и поле
ручного ввода:

| Компонент | Ручной оверрайд |
|---|---|
| Базальный | фиксированное ккал/день (`energy_bmr_mode = manual`) |
| Шаги | «ккал на 1000 шагов» (пересчёт из коэффициента × вес) |
| Силовые | частота / длительность / интенсивность или «своя ккал/сессия» |
| Бытовой | любое ккал/день |

**Удаляется** блок «Уровень активности», enum `ActivityLevel`, `trainingKcal`, `dailyCaloriesBurned`;
`stepsToKcal` обновляется под коэффициент 0.0004. Старые ключи настроек не читаются (миграция без
падений, автомиграции нет — дефолты A.2).

### B.5 Ленивая подсказка профиля

Если BMR не рассчитан (нет HC-записей BASAL и профиль неполон) — карточка-подсказка на «Сегодня»:
«Рассчитаем ваш расход: укажите пол, возраст и рост» → блок B.4. Экран не блокирует.

## 5. Часть C — саммари и движок

### C.1 `WeeklyEnergyStats` (чистый Dart)

Окно = последние 7 дней **исключая сегодня**: `avgIntake` (по дням с данными), `intakeDays`
(покрытие 0–6), `avgExpenditure`, `avgBalance`, `expectedKgPerWeek = avgBalance × 7 / 7700`.
Если дней с приходом < 2 → `null`: энергоблок скрыт, движок работает по старым текстам.

### C.2 RecommendationEngine v2

Сигнатура: `compute({..., WeeklyEnergyStats? energyStats})`. Обратная совместимость обязательна:
без статиков тексты Фазы 5 дословно (регрессионный тест). Со статиками (шаблоны в конфиге,
подстановка движком):

- `inPace`: «Держишь дефицит {balance} ккал/день — темп {actual}%/нед в цели. Оставь рацион без изменений.»
- `tooSlow`: «Темп {actual}%/нед ниже цели {target}%/нед. Средний приход {intake} ккал/день — снизь до {intakeNew} (−{delta} ккал).»
- `tooFast`: «Темп {actual}%/нед выше цели {target}%/нед. Средний приход {intake} ккал/день — добавь до {intakeNew} (+{delta} ккал).»

`{delta}` — динамическая (§0 п. 13, 2026-09-11): `вес × |цель − факт| (п.п.) × 11`, коридор
50–300 ккал, округление до 10; `{intakeNew} = {intake} ∓ {delta}`. Вес — последний
резолвленный на «сегодня».

### C.3 Экран «Саммари»

После существующей карточки — карточка «Энергобаланс недели»: средний приход (покрытие «по 6 из
7 дней»), средний расход, средний баланс, ожидаемый темп из баланса («≈ −0.48 кг/нед»), рядом —
фактический (уже есть выше). Анализ расхождений «ожидание vs факт» — Фаза 8; здесь только числа.

## 6. Разрешения Health Connect (12 → 14 типов)

`kPermissionGroups` (`lib/repo/health_permissions.dart`):

- «Питание»: `NUTRITION` → **READ_WRITE** (ручной «Итог дня»);
- новые группы: «Базальный метаболизм» `[BASAL_ENERGY_BURNED]` READ; «Рост» `[HEIGHT]` READ.

Существующие пользователи получат **один** новый системный диалог (тихий предчек + один пакетный
запрос уже реализованы в `checkAndRequestPermissions`). Регрессионный тест «каждый тип из
`kPermissionGroups` есть в `dataTypeKeysAndroid`» обновляется на 14 типов.

## 7. Загрузка данных (`DashboardViewModel.load`)

- `fetchRawData(NUTRITION)` за 90 дней — в существующий батч; сырые точки сессии
  `_rawNutritionPoints` (перерезолюция при смене решений/источника без похода в HC — B.4/C.4 Фазы 6).
- `fetchRawData(BASAL_ENERGY_BURNED)` за 90 дней.
- `fetchRawData(HEIGHT)` за 365 дней (рост меняется медленно), last-wins → префилл профиля.
- Кеши VM: `_nutritionCache` (`Map<DateKey, NutritionDay>`), `_basalCache`; геттеры:
  `nutritionData` (фильтр диапазона), `expenditureFor(DateKey)`, `balanceData`, `avgCaloriesIn`,
  `avgExpenditure`, `avgMacros`, `targetDeficitKcalPerDay`, `computeWeeklyEnergyStats()`.
- `_reResolveFromRaw()` расширяется на питание; `_reloadDate` — для «Итог дня».
- DebugLog: тег `repo` — `sourceName` точек питания/BASAL; тег `vm` — ввод/правка/удаление итога,
  «Ок/Не ок» для питания.

## 8. Миграции

- Удаление `ActivityLevel` и старой семантики «АКТИВНОСТЬ»: ключи настроек Фазы 5 (`activity_level`)
  перестают читаться — игнорируются без ошибок; новые дефолты — A.2.
- NUTRITION READ→READ_WRITE: выданные READ-права не покрывают WRITE — тихий предчек это увидит
  и покажет один пакетный диалог.

## 11. Порядок реализации и сборки

**A (домен + репозиторий + мок + тесты) → B (экраны) → C (движок + саммари).** Промежуточная сборка
APK после A, финальная после C. Общий DoD: тесты зелёные, `flutter analyze` = базлайн
(4 info / 0 errors), проверки раздела 9 выполнены пользователем на устройстве.
