# System Patterns — Cut Metrics

## Слои архитектуры (текущее целевое состояние)

```
Health Connect (единственный источник истины — вес, шаги; ручной ввод пишется тоже сюда)
      │
HealthRepository (чтение + запись, Фаза 2)
      │
HealthDataProcessor (резолюция по приоритету источников, EMA, Фаза 1)
      │
RecommendationEngine (темп, статус, рекомендация — Фаза 5, чистый Dart, без Flutter-зависимостей)
      │
ViewModel (состояние UI, оркестрация, БЕЗ бизнес-логики)
      │
UI (Фаза 3 — состояния подтверждения; Фаза 5 — индикатор источника)
```

`AccessGate` (paywall) — намеренно НЕ в этой схеме, отдельная будущая фаза.

## Ключевые архитектурные решения и их обоснование

### Без собственного бэкенда
Решено сознательно после сравнения альтернатив. Health Connect — локальное зашифрованное
хранилище на устройстве, поддерживает запись (не только чтение) и хранит метаданные `dataOrigin`
на каждой записи. Из-за этого не нужен свой сервер/БД/авторизация для MVP. Компромисс: нет
кросс-девайс синхронизации через API, нет моста с iOS/HealthKit — принято сознательно.

### Приоритет источников — двухуровневая модель (Фаза 1)
- **Tier 1** — запись с `dataOrigin` = наш пакет (ручной ввод пользователя) — всегда побеждает
  для своей даты, если существует.
- **Tier 2** — внешние источники (фолбэк, когда Tier 1 отсутствует):
  - Вес — last-wins по времени записи (не cumulative-тип, платформенного приоритета нет).
  - Шаги — через нативный Health Connect `aggregate()` (учитывает приоритет источников из
    настроек ОС, НЕ из нашего кода) — не суммирование сырых записей, иначе задвоение при
    нескольких источниках.

### Отмена ручной коррекции
Естественное свойство модели: удаление Tier 1-записи автоматически откатывает на Tier 2 при
следующей резолюции — отдельной логики "отката" нет.

### Без локального кэша/БД (Фаза 4)
Полный пересчёт из Health Connect при каждой загрузке, без drift/sqlite/Hive для данных здоровья.
Безопасно именно потому, что Health Connect — локальный источник, не сеть (см. выше). Сессионный
in-memory кэш ViewModel (`_weightCache` и т.п., уже существует в коде) — остаётся, это другое:
оптимизация в рамках одного запуска, не персистентность.

⚠️ Критично: резолюция по приоритету (Фаза 1) должна быть реализована батчево на весь диапазон
дат, а не отдельным запросом на каждый день — иначе холодный старт станет медленным.

### UX-поток подтверждения значения (Фаза 3)
5 состояний на пару (дата, метрика): `loading` / `missing` / `autoUnconfirmed` /
`manualEntryActive` / `manualConfirmed`. Доступно для ЛЮБОЙ даты, не только "сегодня" — точка
входа через тап по графику (`fl_chart`, уже в проекте) или напрямую на экране "Сегодня".
Блокировка при `missing` — только карточка метрики, не весь экран. "Ок" не имеет побочных
эффектов на данные (согласовано с отказом от кэша).

### Правка исторической даты веса влияет на EMA вперёд
EMA — скользящее среднее, правка прошлой даты меняет тренд для всех дат после неё. Шаги — не
затрагиваются (не последовательны).

## Известный технический долг (из `docs/cut_metrics_project_map.md`, не решается автоматически)
- `WeightDay` не имел `==`/`hashCode` — чинится в Фазе 1 заодно.
- EMA пересчитывается целиком при каждом `setDate()` — принимается как есть, не оптимизируется
  в текущих фазах.

## Порядок фаз реализации

1. Модель данных и приоритет источников — `docs/cut_metrics_phase1_data_model_spec.md`
2. Repository: чтение и запись — `docs/cut_metrics_phase2_repository_write_spec.md`
3. UX-поток подтверждения значения — `docs/cut_metrics_phase3_confirmation_ux_spec.md`
4. Без локального кэша — `docs/cut_metrics_phase4_no_cache_spec.md`
5. RecommendationEngine и индикатор источника — `docs/cut_metrics_phase5_recommendation_and_indicator_spec.md`
   (+ дополнение по итогам сбора требований: `docs/phase5_ui_screens_and_activity_spec.md`)
6. (Будущее, вне текущего скоупа) AccessGate / монетизация

Фазы зависят друг от друга последовательно — не реализовывать фазу N+1, не завершив то, что
зафиксировано в Definition of Done фазы N, если явно не попросят иначе.

## Паттерны Фазы 5 (2026-08-21, зафиксированы по итогам сбора требований)

### Все константы Фазы 5 — в одном файле
`lib/domain/recommendation_config.dart`: период EMA движка (7), tolerance (±0.15 п.п.),
минимум точек (3), дефолт темпа (0.8%), границы/шаг слайдера, коэффициент шаг→ккал,
диапазоны (90/30 дней), тексты саммари и снекбаров. Требование пользователя — правка
«чисел под калибровку» должна быть в одном месте.

### Саммари: ежедневный пересчёт, а не еженедельный цикл
A.6 исходной спеки отменён: саммари пересчитывается при каждом открытии вкладки за
скользящие 7 дней. Гейт — в `main.dart::_selectTab`: не готово → снекбар, вкладка не
открывается. `lastSummaryShownDate` пишется при показе, но НЕ гейтит (хранится на будущее).

### Нормализация темпа к неделе
`pace = ΔEMA% × 7 / (дни между крайними точками окна)` — без этого 3 точки за 2 дня
давали бы заниженный в ~3 раза темп (почти всегда tooSlow). Сравнение с целью — по |pace|
(набор веса при цели снижения = tooSlow).

### Активность = шаги + уровень, без EXERCISE_TIME
`kcal = шаги × вес × 0.0005 + kcalPerKgPerDay(уровень) × вес`. Уровни 1–5:
0/1.5/3.0/4.5/6.0 ккал/кг/день. День без записи шагов = 0 шагов, добавка уровня
начисляется всегда. Вес — самый свежий из кеша; нет веса → калории «—».

### Сон: перенесён из old_proj, но с послойным merge
`SLEEP_ASLEEP` (общая длительность) приоритетнее суммы стадий (DEEP+LIGHT+REM).
Merge интервалов выполняется по слоям (стадии отдельно, ASLEEP отдельно) — сквозной
merge обрезал бы стадии, лежащие внутри общего интервала. Пустые ночи не попадают в
кеш (исключаются из среднего). Чтение — с запасом −1 день (ночь пересекает полночь).

### Предзагрузка за 90 дней независимо от сегмента Тренда
`load()` всегда грузит вес/шаги/сон за `maxTrendDays` (90) — движку рекомендаций нужен
вес за окно независимо от того, какой сегмент смотрит пользователь. `setRange(7/30/90)`
только фильтрует кеши, без похода в Health Connect. «Весь срок» убран как сегмент.
